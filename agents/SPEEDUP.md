# Оптимизации отрисовки (план)

Задача: подлагивание при отрисовке/сдвиге карты на слабых машинах.
Анализ сделан 2026-10-26 по текущему `index.js`. Номера строк со временем
устареют — ориентир на имена функций. Контекст: в активной кампании
(`custom/pokras-spc`) ~96 объектов, карта — большой PNG; каждый mousemove
при перетаскивании вызывает полный `drawCanvas()`. Состояние и формат
сейва не меняются ни в одном пункте.

## Найденные проблемы и предлагаемые фиксы

### 1. Шахматный фон перерисовывается тысячей вызовов каждый кадр — главный тормоз

`drawCanvas()`: вложенный цикл `fillRect` по клеткам 20px
(`gridSize = 20`). При окне 1920×1080 это ~5200 вызовов fillRect
и столько же установок fillStyle **в каждый кадр**, включая каждый
mousemove при драге. На слабых машинах — доминирующая цена всего кадра.

**Фикс (дёшево):** один раз (при resize/инициализации) отрисовать фон
в offscreen-canvas, в `drawCanvas()` — один `ctx.drawImage(bg, 0, 0)`.
Альтернатива — `createPattern()` из тайла 40×40 и один `fillRect`.
~5–20 строк.

### 2. Перерисовки не сгруппированы по частоте кадров (rAF)

`Pointer.updateDrag()` вызывает `drawCanvas()` на каждый mousemove —
мышь шлёт события чаще 60 Гц. Каждый кадр рисуется: фон (см. №1),
карта целиком, все объекты, туман.

**Фикс:** объединять перерисовку через `requestAnimationFrame` с флагом
«перерисовка запрошена»:

```js
let repaintQueued = false
function requestRedraw(options) { // сохранить последние options
  if (repaintQueued) return
  repaintQueued = true
  requestAnimationFrame(() => { repaintQueued = false; drawCanvas(options) })
}
```

Заменить прямые вызовы `drawCanvas()` в `updateDrag` / `handleMove` /
`handleWheel` на `requestRedraw()`. Из окна три подряд события мыши
рисуются одним кадром вместо трёх.

### 3. Карта рисуется целиком в кадр (из видимой — четверть)

`ctx.drawImage(map.image, ...)` в `drawCanvas()` рисует картинку целиком.
Браузер отсекает лишнее, но при zoom-out (0.25–0.5) это самый дорогой
blit. Дополнительно: при каждом прокручивании колеса тоже вызывается
`drawCanvas()`.

**Фикс:**
- рисовать только видимую часть карты исходниковым прямоугольником:
  `drawImage(map, sx, sy, sw, sh, dx, dy, dw, dh)`, где видимая область
  в мировых координатах = экранная, минус `Viewport.offsetX/Y`, делённая
  на `Viewport.scale`. Выигрыш при слабом GPU;
- отсоединить перестройку DOM-инфо-панели от самого кадра (см. №4).

### 4. Инфо-панель пересобирает innerHTML на каждый кадр

`UI.drawInfoPanel()` при каждом вызове:
1) `userEffectsObj.sumPlayerEffects(player)` — обходит все элементы;
2) строит и присваивает `innerHTML`.
Вызывается в `drawCanvas({infoPanel: true})`, в т.ч. при колесе мыши и
ряде кликов.

**Фикс:**
- debounce: при драге/колесе панель обновлять не чаще ~5–10 Гц;
- кеш `sumPlayerEffects` по ключу (цвет игрока + `CURRENT_TURN`),
  сброс там же, где сейчас сбрасывается `TechUtils.techEffectCache`
  (конец хода / загрузка).

### 5. Canvas-текст — сводить элементы к спрайтам (запасной шаг, НЕ сейчас)

В `draw.customObj` на каждый элемент: figure + emoji/image + `textBelow`
(установка `ctx.font`) + `strokeText`/`fillText` для lvl. Canvas-текст —
самая медленная примитивка. При ~100 объектах приемлемо; если прироста
п.1–4 не хватит — прендерить уникальные спрайты в offscreen-canvas с
кешем по `(name, color, curr_hp, lvl, disabled, endedTurn)` и на кадр
делать только `drawImage`. Больший рефакторинг, делать отдельно и
осознанно. Спрайт-кеш инвалидируется при изменении HP/lvl/disabled.

### 6. Мелочи (по остаточному принципу)

- `canvas.getBoundingClientRect()` на каждом mousemove в
  `Pointer.updateDrag` — кешировать, инвалидируя при scroll/resize.
- `draw.fogOfWar`: при включённом тумане каждый кадр — full-screen fill
  + N clearRect. Возможен пропуск перерисовки тумана при действиях,
  не затрагивающих видимость (сдвиг Viewport, драг чужого юнита),
  но это хрупкая логика — только по явному желанию.
- DPR: canvas рендерится в CSS-пикселях, на HiDPI браузер сам его
  растягивает — это сама быстрая настройка по умолчанию на слабых
  машинах, не трогать.

## Замеры 2026-11-02 (pokras-spc) и вынос заднего плана в world-canvas

Замер в браузере на активной кампании (карта 2640×2496, 625 квадратов
сетки, 100 объектов, viewport ~750×700, zoom ~92%); среднее по 20
прогретым вызовам:

| блок кадра | мс |
|---|---|
| blit картинки карты (`drawImage(map)`) | ~5 |
| `SquareGrid.draw` (линии + 625 подписей; биомов 0) | ~20 |
| **итого «задний план» (кандидат на вынос)** | **~25** |
| все элементы (`draw.element`, 100 шт) | ~390 (~4 мс на объект!) |
| туман войны (`draw.fogOfWar`) | ~10–25 |
| полный `drawCanvas()` | ~320–390 |

Выводы: (а) подписи клеток `fillText` — самая дорогая часть сетки;
(б) основной тормоз — элементы и туман: они рисуются каждый кадр
независимо от заднего плана и в этот пункт не попадают; (в) задний
план сегодня рисуется в каждом `drawCanvas()` (пан, драг, hover в
биом-редакторе).

**Предложение: offscreen-canvas размером с карту в мировых
координатах** (по образцу существующего `getBackgroundCanvas`):
- один раз отрисовать туда карту + `SquareGrid.draw` (~20 мс);
- `drawCanvas()` вместо двух вызовов делает один `drawImage` с тем же
  translate/scale — замер: ~0.05 мс;
- пан/драг/hover задний план не перерисовывают вообще;
- смена биома в редакторе или зума — редкие события: перерендер
  world-canvas ~20 мс разово, глазу не заметен.

Выигрыш/память: экономия ~25 мс в каждый кадр (пан, драг, hover);
offscreen 2640×2496 ≈ 26 МБ (приемлемо для десктопа).

**Вынос убирает ~25 мс из кадра ~350 мс (~7%)** — заметно только
в связке с rAF-скоуплением №2; основной кандидат на ускорение —
кеш спрайтов элементов (№5, ~390 → десятки мс).

**Точки инвалидации (главный риск — пропустить одну):**
1. `loadMaps`/`loadMap` и `loadDefaultData` — смена карты;
2. `SquareGrid.setBiomes` — загрузка сейва;
3. `SquareGrid.setBiome` — краска биомов в редакторе;
4. смена зума (`Viewport.handleWheel`/`updateScale`) — иначе линии и
   подписи заметно мылятся при растяжении; мягкий вариант — не
   инвалидировать (карта и так растянута тем же трансформом).

**Обязательное сопутствующее:** `biomeActionsObj.drawHover` вывести
из блока карты в `drawCanvas` (строки ~1428–1434) в динамический
слой после элементов — hover меняется при mousemove, а заодно он
становится дешёвым. Туман уже на отдельном `fog-canvas`, шахматка
уже кешируется (`getBackgroundCanvas`) — их не трогаем;
`renderFullFieldCanvas` (PNG-экспорт) рисует карту сама — позже можно
переиспользовать world-canvas.

## Порядок работ

Шаги делать **по одному**, после каждого — прогон `Tests.html` через
локальный сервер + визуальная проверка `custom/pokras-spc.html`
(см. `AGENTS.md`). К моменту плана тестов 20, ожидание
«Пройдено: 20, упало: 0» — актуальное число смотреть в `AGENTS.md`
(на 2026-11-02: 35 тестов).

1. **Кеш фона** (№1) — ✅ сделано (2026-10-31): offscreen-canvas
   `getBackgroundCanvas()` в `index.js`, инвалидация по сравнению размеров
   с `canvas` (перестройка при resize происходит сама, на первом кадре
   после него). Замер в браузере (окно 1030×720): полный кадр с кешем
   ~0.37 мс, один только старый цикл фона стоил ~0.48 мс.
2. **Вынос заднего плана в world-canvas** (см. «Замеры 2026-11-02») —
   карта + сетка + биомы один раз, `drawCanvas()` — один blit;
   инвалидации: карта/сейв/биом-краска, зум — по желанию;
   `drawHover` перенести в динамический слой.
3. **rAF-скоупление перерисовок** (№2) — заметнее в связке с шагом 2;
   тест: 3 вызова `updateDrag` подряд → 1 фактический кадр
   (spy на `drawCanvas`).
4. **Профилирование `draw.element` → минимальный фикс** — по замерам
   2026-11-02 элементы — главный тормоз кадра (~4 мс на объект;
   подозрительно много даже для canvas-текста: вероятны повторные
   cache-miss картинок, лишние save/restore или тени). Сначала
   `console.time` вокруг отдельного цикла рисовки одного объекта, фикс
   без кеша, мерить снова; спрайтовый кеш (№5) — только если
   запас не выкачан.
5. **Кеш спрайтов элементов** (№5) — самый большой резерв
   (~390 → десятки мс), тяжёлый рефакторинг с инвалидациями по
   `curr_hp/lvl/disabled/endedTurn`; делать после шага 4 по его
   итогам.
6. **Видимая часть карты + отделение инфопанели** (№3/№4 частично).
7. **Кеш `sumPlayerEffects` + debounce панели** (№4).

## Ограничения и совпадения с конвенциями

- `index.js` остаётся единым файлом, без IIFE и ESM; новые хелперы —
  глобальные (`requestRedraw`, кеши внутри существующих объектов-модулей
  вроде `Viewport`/`UI`), см. `REFACTORING.md`.
- Тесты обращаются к глобалам движка; если `drawCanvas` станет
  вызываться непрямым путём, тесты через spy не сломаются —
  лучше сохранять глобальное имя функции.
- Автопроверка: `console.time('draw')`/`console.timeEnd('draw')` уже
  есть в начале/конце `drawCanvas()` (закомментированы) — раскомментировать,
  чтобы замерить «до/после» до и после работ.
